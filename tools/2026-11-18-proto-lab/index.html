        说明
        Proto Lab 做什么、按什么口径、怎么验证的。
        
          
        能做什么
        
          
          
            
        • 解码：粘贴十六进制、Base64（含多段拼接的 gRPC-web-text）、"\x08\x96\x01" / "\010\226\001" 转义串、[8, 150, 1] 或 []byte{0x08, …} 数组，或者直接读二进制文件。不选类型时按 protoc --decode_raw 的规则原始解码；选了消息类型或某个 RPC 的请求 / 响应，就按 schema 解码成文本格式与 proto3 JSON。
          • 
            
        • 字节视图：每个字节按角色着色（tag、长度前缀、四种 wire type、组结束、gRPC 帧头），未知字段带红色虚线。点任意字节就定位到它所属的字段，检视区同时给出 varint 的 uint64 / int64 / int32 / ZigZag / bool 读法、定长的整数与浮点读法、LEN 的文本 / 子消息 / packed 读法。
          • 
            
        • 编码：proto3 JSON 或 protoc 文本格式 → 线格式字节，可输出十六进制、Base64、C 转义串、Go / Python / JavaScript / Java 字面量；默认确定性（字段号升序、map 按键的 UTF-8 字节序排序），也可以按书写顺序（同 protoc --encode）。编码后自动解回来做往返校验。
          • 
            
        • Schema：多文件项目，import 互相引用，google/protobuf 的 Timestamp、Duration、Any、Struct、FieldMask、Empty 与包装类型已内置。作用域解析照 protoc 的规则（先在内层作用域找首段名字），报错带文件:行:列。
          • 
            
        • 兼容性检查：旧版与新版 schema 对比，规则名与 buf breaking 一致，分 WIRE（只看二进制）与 WIRE_JSON（二进制 + JSON）两档。
          • 
            
        • 体积分析：每个字段自身占多少字节、tag 与长度前缀开销、和同内容 JSON 的对比，以及能核算出节省字节数的建议（负数换 sint、大数换 fixed、未打包的 repeated、高频字段的字段号）。
          • 
          
        
          
        口径
        
          
          
            
        • 文本格式与 protoc 35.1 逐字一致：字符串里的非 ASCII 字节一律写成三位八进制；double 先试 15 位有效数字，读回不等再用 17 位；float 先试 6 位再用 9 位（非规格化数直接 9 位）；指数至少两位（1e-05）；map 条目按键排序打印且总是同时写出 key 与 value；未知字段放在最后。
          • 
            
        • 原始解码时，LEN 字段只要非空、能整段读成消息就当子消息显示，否则当字符串。这是 protoc 的猜法，会猜错：示例里的字符串 "Hi" 恰好是合法消息 { 9: 105 }，packed 的 [1, 2, 300] 则显示成字符串 "\001\002\254\002"。
          • 
            
        • 按 schema 解码时：wire type 与声明不符的字段按未知字段保留；proto2（封闭枚举）里没有的枚举值也进未知字段；proto3 的 string 必须是合法 UTF-8，否则整条消息解析失败；重复出现的单值子消息会合并，标量取最后一个；嵌套上限 100 层。
          • 
            
        • JSON 映射：64 位整数输出为字符串，bytes 为标准 Base64（输入也认 URL 安全写法、可不补 =），float 输出最短往返写法，NaN / Infinity 用字符串；数字按原文无损解析，所以 "9007199254740993" 不会丢精度。
          • 
            
        • 暂不支持 editions（edition = "2023"）与自定义选项的取值，只做语法检查；未提供的 import 只警告，用到其中的类型才报错。
          • 
          
        
          
        怎么验证的
        
          
        离线对拍共 143,951 项，全部通过：原始解码对 protoc --decode_raw 3,600 例（含 787 例 protoc 也拒收的坏输入）；按 schema 解码对 protoc --decode 6,707 例（42 份随机 proto2 / proto3 schema，含组、扩展、封闭枚举、map 重复键与各种变异）；编码对 Python protobuf 与 protoc --encode 逐字节 3,024 例；JSON 对 Python json_format 2,192 项（Python 与 protobuf-es 两家一致的子集上 947/947 全对）；schema 编译对 protoc 的接受 / 拒绝与描述符 550 项；兼容性对 buf 1.75.0 1,040 项（520 对随机 schema 演进 × WIRE / WIRE_JSON 两档，规则、位置、行号逐条一致）；往返与 %.*g 格式化性质 126,838 项。
        
          
        对拍期间抓到并修好的引擎问题 8 处，例如：protoc 判断「LEN 像不像子消息」时 tag 与长度都按老式读法最多 10 字节、只取低 32 位；proto2 的 string 不校验 UTF-8、要原样保留字节；JSON 里 float 的 -0.0 不能写成 0；buf 把 enum 单独算一个线格式组、required ⇄ optional 也算基数变化。
        
          
        口径差异（不算失败）：Python 读不回它自己打印的 float 最大值 3.4028235e+38，本页按 Go / Java 的做法接受；JSON 往返时 Any 里的字节会按确定性顺序重新编码，语义相同但字节可能不同；map 有重复键时文本格式像 protoc 一样列出全部条目，JSON 与编码取最后一条。
        
          
        对拍脚本与结果保存在本期运行目录；浏览器测试还会逐条比对页面输出与 protoc / Python / buf 现场算出的真值。
